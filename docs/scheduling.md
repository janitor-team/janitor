# How work is scheduled

(codebases)=

## Codebases

The Janitor only works on {term}`codebases <codebase>` it knows about. A
codebase is mostly static information about one place in a VCS repository: a
name, the version control information (VCS type, URL, branch, subpath) and
optionally a `value`, for example the popularity of the package.

This repository has no importer for a package archive, so each instance's own
setup builds a JSON list of its codebases and POSTs it to the runner's private
`/codebases` endpoint (port 9911 in the container image). For example:

```console
$ cat codebases.json
[{"name": "hello", "url": "https://github.com/example/hello",
  "branch": "main", "vcs_type": "git", "value": 10}]
$ curl -X POST -H 'Content-Type: application/json' \
    --data @codebases.json http://localhost:9911/codebases
```

Each item can have:

- `name`: the codebase name, which candidates give in their `codebase` field.
  At least 2 lowercase letters, digits or `+-.`, starting with a letter or
  digit. One invalid item makes the whole upload fail (HTTP 500).
- `url` and `branch`: where the code lives (`branch_url` is the old form)
- `subpath`: a subdirectory, if the codebase is not the whole branch
- `vcs_type`: the VCS, e.g. `git` or `bzr`
- `vcs_last_revision`: the last known revision, if any
- `value`: how important the codebase is, relative to the others
- `web_url`: a page for people to look at

## Candidates

Once the Janitor knows about a codebase, candidates can be created. A
{term}`candidate` is a record saying that a particular campaign (e.g.
`lintian-fixes`) can be run on a particular codebase, and that there is some
chance it will yield changes.

Candidates include information like:

- `value`: a relative number that says how useful this change would be
- `success_chance`: an estimate of how likely this change is to succeed and
  result in a build
- `context`: some indicator of the current state of the world, used to avoid
  retrying builds if nothing has really changed. For example, for new upstream
  releases, this is the upstream version number of the latest release.
- `publish-policy`: the name of the {term}`publish policy`, which says what to
  do with a successful run (see {doc}`How Janitor works </devnotes/overview>`)

Like codebases, candidates are generated by a script. Its JSON output is
POSTed to the runner's `/candidates` endpoint. Candidate generation scripts
can be really complicated, allowing for better scheduling, or really simple,
in which case they just output a candidate for each codebase in a campaign
with fixed settings for `value` and `success_chance`.

## Scheduling

When candidates are uploaded, the runner adds each of them to the queue
straight away. The schedule job, `janitor-schedule`, adds the queue entries
again for every candidate that has a publish policy. Nothing runs it for you,
and no container image ships it, so run it regularly (from cron or a systemd
timer, for example).

The position in the queue takes into account:

- `value` of the candidate, plus a bonus for each branch its publish policy
  pushes or proposes, and a bonus for the first run
- `value` of the codebase, relative to the highest one
- previous success rate for the campaign/codebase combination, ignoring
  {term}`transient` failures
- previous run duration
- whether the `context` has changed since the last run

The queue consists of prioritized {term}`buckets <queue bucket>`. Manually
requested runs, runs triggered by the publisher (e.g. to resolve merge
conflicts) and retried runs are always executed before runs that were scheduled
by the scheduler.

Next, workers take items from the queue and the publisher publishes the
results, see {doc}`How Janitor works </devnotes/overview>`.
